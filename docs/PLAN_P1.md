## 1. Q-0001 · P1 先做哪条主线

| 主线 | 涉及改动面 | 新增概念 | 主要风险 | 验收标准 | 粗估 |
|---|---|---|---|---|---|
| **A. 会话格式 v4** | `internal/session` 拆分重写（types / store / persist / migrate）、`agent.Loop` 的投影改造、`server` 会话读取、迁移测试 | header + event 信封、单写者锁、generation、崩溃尾部修复、v0→v4 迁移链 | **数据不可逆**：格式选错，后续所有读写都背着；需要真实历史样本验证 | 能写 v4 JSONL 并读回；并发写只有一个写者；进程被杀后尾部可修复；旧会话只读打开不损坏 | 最大（多个会话） |
| **B. 流式 SSE** | `internal/llm`（新增**可选** `StreamingClient` 接口，不动 `Client`）、`deepseek.go` 的 SSE 解析、`agent.Loop` 事件、`server` 的 `/api/chat` SSE 分支、`index.html`、CLI 打印 | 增量 token 事件、工具调用进度、断线语义 | 低：可与现有非流式并存，不破坏契约 | Web 逐字输出；工具执行期间有进度；断线不影响后续请求 | 中 |
| **C. 工具补齐** | `internal/builtin` 新增 `edit`/`glob`/`grep`/`todo_write`/`read_image` + 各自测试 | 每个工具一个 `tool.Tool` 实现 | 最低：纯增量，不动既有路径 | `dsh tools` 可见；真实读写通过；路径沙箱沿用 | 小-中（工具越多越线性） |

**建议**：**A 先行**。理由：

1. 会话格式是数据基座——后面所有能力（流式落盘、工具批次、projection、telemetry）都建立在事件模型上，越晚改越贵；
2. 与 Q-0004 是同一批工作（拿上游样本当黄金验收），合并做比拆开做省一半验证成本；
3. B 的风险虽低，但流式落盘的事件形状依赖 A 的事件模型，先做 B 等于先把落盘逻辑写两遍。

**但**如果你更想尽快看到"能用的能力"，顺序可以反过来（C → B → A），代价是 A 落地时上述两块要跟着改一次。

## 3. Q-0003 · 是否规范行尾

- **现状**：Windows 工作区每次 `git add` 都刷 `LF will be replaced by CRLF` 警告；仓库内混有 LF/CRLF 的历史文件。
- **B 的具体动作**：加 `.gitattributes`（`* text=auto eol=lf`）+ 一次 `git add --renormalize .` 提交。
- **代价**：会产生**一次纯行尾的大 diff**（内容不变）；之后 diff 干净、跨平台一致。
- **收益**：CI 的 `gofmt` 校验在 Linux 上才有意义（否则 Windows 检出的 CRLF 会让 gofmt 全量报错），长期看是必须的。
- **建议 B**，且**越早越省**——仓库还新，renormalize 的噪音最小。

## 4. Q-0004 · 是否与上游 TS 做 session 互操作验证

- **现状**：上游源码已 clone 在 `%USERPROFILE%\Desktop\deepseekharness`（只读），其中 `docs/session-format-status.zh.md` 与 `session-format*` 包是 v4 的权威定义。
- **价值**：v4 实现最大的风险是"格式理解偏差"，只有读真实上游会话文件才能证伪；同时能让 Go 版直接打开桌面应用的历史会话。
- **代价**：需要在 A 的验收里加一组"读上游样本"的用例，多花约半天。
- **建议 B**：与 A 同批做。若不做，A 的验收只能靠自造的 happy-path 样本，风险留在发布后。
