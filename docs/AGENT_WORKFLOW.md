# Agent 工作流与记录规范

本文件是 [AGENTS.md](../AGENTS.md) 的展开说明，给出可直接照做的任务流程、记录模板用法和多 Agent 编排示例。
模板文件：

- 任务记录：[tasks/TEMPLATE.md](tasks/TEMPLATE.md)
- 决策记录：[decisions/TEMPLATE.md](decisions/TEMPLATE.md)

---

## 0. 会话开始检查清单（5 分钟）

```text
[ ] 读 AGENTS.md
[ ] 读 docs/STATUS.md（当前阶段 / 进行中 / 待决策）
[ ] 读本次相关 docs/tasks/ 与 docs/decisions/ 记录
[ ] git status / git log -5 / 当前分支
[ ] 确认环境：go version、构建是否可用（必要时跑一次 go test ./...）
[ ] 确认密钥状态：只检查是否设置，不打印明文
[ ] 明确本次任务的验收标准；任务较大时先拆分成任务记录再动手
[ ] 检查 docs/STATUS.md 决策队列：存在未决项时，本轮只提交决策表格，**不实施**
```

如果以上有信息缺失（例如没有对应任务记录），先补记录再实施。

## 1. 任务生命周期

```text
预检 → 登记(todo) → 决策表格(如有，等待用户逐项决策) → 用户说"实现" → 实施(doing) → 验证 → 收尾(done/blocked) → 交班
```

> 实施门禁（D-0002）：存在未决决策时禁止开始实施；只有用户明确说"实现"才切换到施行阶段。

### 1.1 登记

在 `docs/tasks/` 新建 `T-XXXX-<slug>.md`（编号在 `docs/tasks/README.md` 索引中递增），至少包含：

- 目标（一句话）与非目标（明确不做什么）
- 范围与写作用域（涉及哪些包/文件/目录）
- 验收标准（可执行的检查项）
- 依赖与风险
- 新建任务后同步更新任务索引，并在 `docs/STATUS.md` 的「进行中」登记

### 1.2 决策

- 用户明确拍板 → 写 `docs/decisions/D-XXXX-<slug>.md`，在任务记录中链接决策 ID。
- Agent 自主决策 → 写在任务记录「自动决策」小节：决策、理由、影响。
- 需要用户拍板但用户未答复 → 任务状态写 `blocked`，`docs/STATUS.md` 登记「待用户决策」。

### 1.3 实施

- 每次只推进一个可验证增量；先写测试或明确验收命令。
- 不夹带需求外改动；发现的改进想法写入任务记录「范围外发现」。
- 多 Agent 并行时严格遵守写作用域互斥（见 §5）。

### 1.4 验证

在任务记录中记录**命令 + 结果摘要**，而不是只写"测试通过"。示例：

```text
$ go test ./... → ok 8 个包，全部通过（0.4–1.3s）
$ go vet ./... → exit 0
$ staticcheck ./... → exit 0
$ .\scripts\build.ps1 → built bin\dsh.exe (commit 3b412be)
$ python scripts/check_md_links.py → md_files=14 relative_links_checked=38 missing=0（文档改动必跑）
真实验证：DEEPSEEK_API_KEY 设置后 dsh chat --prompt "..." → 回复 xxx（附会话文件路径）
```

### 1.5 收尾

- 任务记录状态改为 `done`（或 `blocked`/`cancelled` 并说明），补齐验证结果、遗留问题、下一步。
- 更新任务索引、`docs/STATUS.md`、必要的 README/ARCHITECTURE。
- `git status` 确认干净，按 [AGENTS.md §7](../AGENTS.md) 提交。
- 向用户报告：做了什么 / 证据 / 影响与风险 / 待决策。

## 2. 任务记录写法

原则：**让下一个会话无需翻聊天记录即可接手**。

必须写清：

| 章节 | 内容 |
|---|---|
| 元信息 | ID、标题、状态、日期、负责人（Agent 名）、关联决策 |
| 目标 / 非目标 | 做什么、明确不做什么 |
| 范围 | 涉及文件/包/目录（写作用域） |
| 验收标准 | 可执行的检查清单 |
| 实施步骤 | 实际走的步骤，关键选择与理由 |
| 自动决策 | Agent 自主决定的事项及原因 |
| 验证记录 | 命令 + 输出摘要 + 真实验证结果 |
| 文件清单 | 新增/修改/删除的文件 |
| 遗留 / 下一步 | 未完成、已知问题、下一步入口 |
| 范围外发现 | 值得做但不属于本任务的事（等待用户决策） |

粒度建议：一次提交/一次验证/一个关键决策各记一段。

## 3. 决策记录写法

### 3.1 两类决策

| 类型 | 记录位置 | 示例 |
|---|---|---|
| 用户决策 | `docs/decisions/D-*.md` | 范围、接口、依赖、优先级、安全策略、交互风格 |
| Agent 自动决策 | 任务记录「自动决策」 | 实现细节、内部命名、测试组织、不影响接口的重构 |

### 3.2 用户决策记录必填

- 决策 ID（`D-XXXX-NN`）、日期、任务归属
- 背景与问题（为什么会走到这个决策点）
- 选项（至少 2 个，含被否决项与理由）
- 最终决定与决策人
- 影响面（代码/数据/文档/兼容性）
- 回滚方式
- 关联任务/提交/文档链接

### 3.3 规则

- 决策记录**只追加不覆盖**；结论变化时新增一条决策并注明"取代 D-XXXX-NN"。
- 不得替用户做范围、安全、成本、产品类决策；未答复时任务保持 `blocked`。
- 决策一旦落盘，后续实现必须遵循；如发现决策不可行，先回到用户重新决策。

### 3.4 会话内决策表格与实施门禁（D-0002）

存在需要用户拍板的问题时，必须在**会话回复末尾**给出编号表格，并与 `docs/STATUS.md`「决策队列」同源：

| ID | 待决问题 | 选项 | 建议 | 影响 | 状态 |
|---|---|---|---|---|---|
| Q-0001 | 示例：P1 先做哪条主线？ | A. 会话格式 v4 / B. 流式 SSE / C. 工具补齐 | A | 决定后续 1–2 周任务顺序 | 待决策 |

规则：

1. **逐项决策**：用户按 ID 给结论（如 `Q-0001=A`）；未决项维持"待决策"。
2. **实施门禁**：存在未决项时，相关任务保持 `todo`/`blocked`，**不得开始实施**。
3. **显式授权**：只有用户明确说"实现"（或等价明确授权）后，才可进入实施；逐项批准决策 ≠ 实施授权。
4. **持续可见**：每轮回复若有未决项，末尾保留最新决策表格；已决项标注结论。
5. **落盘**：决策完成后写入 `docs/decisions/D-XXXX`、更新任务记录、队列状态改 `resolved`，再进入实施与质量门禁。
6. 代理不得自行把"待决策"当成"默认同意"；用户未答复即视为未决策。

## 4. 状态管理与跨会话交接

`docs/STATUS.md` 是**唯一实时入口**，每次会话结束前更新：

```markdown
## 当前阶段
## 环境事实（工具链/密钥是否配置/数据目录）
## 进行中（任务 ID + 一句话进度）
## 下一步候选（按优先级）
## 待用户决策（问题 + 选项 + 推荐）
## 最近验证（命令 + 结果）
```

交接说明（写给下个会话/用户）应包含：

1. 上次停在哪、为什么停
2. 已修改/新增的关键文件
3. 未验证或存在风险的部分
4. 下一个动作（命令/文件/决策点）

## 5. 多 Agent 编排实操

### 5.1 拆分触发条件

- 预估 > 2–4 小时；或存在可独立推进的多个子域；或需要并行调研/审计/验证。
- 拆分本身也有成本：子任务数量控制在 2–5 个为宜，超过时先合并同域工作。

### 5.2 拆分与写作用域示例

```text
根 Agent（Lead）
├─ T-0010 会话格式 v4 实现（子 Agent A）
│   写作用域：internal/session/**, docs 中仅限本任务记录草案
├─ T-0011 流式 LLM 客户端（子 Agent B）
│   写作用域：internal/llm/**
├─ T-0012 工具补齐（子 Agent C）
│   写作用域：internal/builtin/**, internal/tool/testdata/**
└─ 根 Agent：集成、全量测试、文档定稿、commit
```

要求：

- 每个子任务在任务板登记：目标、写作用域、依赖、验收标准。
- 有顺序依赖的任务设置 `blocked_by`，不并行推进。
- 根 Agent 在合并前必须：`git diff` 审查 + 全量测试 + 真实场景验证。
- 子 Agent 不得直接修改共享索引 / STATUS / AGENTS.md（由根 Agent 定稿）。

### 5.3 集成检查清单

```text
[ ] 所有子任务状态与写作用域核对无冲突
[ ] git diff 逐个文件审查（无越界改动、无调试残留）
[ ] gofmt / vet / staticcheck / test / build 全绿
[ ] 真实场景验证（涉及模型/网络/文件系统）
[ ] 任务记录 + STATUS + 索引更新
[ ] commit 拆分合理、信息可回溯
```

## 6. 常见反模式（禁止）

| 反模式 | 正确做法 |
|---|---|
| 只在会话里说明决策，不落盘 | 写进任务/决策记录 |
| 顺手扩展需求范围 | 记入「范围外发现」，等用户决策 |
| 为风格大量重命名 | 不重构；有证据时单独重构提交 |
| 报告"测试通过"但不给命令/结果 | 附命令与输出摘要 |
| 多 Agent 同时改同一文件 | 写作用域互斥，排队执行 |
| 把密钥写进配置/文档/日志 | 仅环境变量，检查 diff |
| 会话结束不更新 STATUS | 每次都更新，形成接力 |
| 大改动一次提交 | 拆分为可回滚的小提交 |
