## 优先级决策（2026-11-22，代理受权拍板）

**顺序 = 小件 → 死局 → 安全地基 → 输出/上下文治理 → 生态与运维**：

| 波段 | 内容 | 理由 |
|---|---|---|
| 1 | B-35 / B-31 / B-32 / B-34 | 半小时级、无依赖、用户每天碰得到；让小批次就有可见产出 |
| 2 | B-14 / B-40 / B-43 | 补 P1 最后一条验收 + 把 staticcheck 与重试回归装进 CI，给后面改动装网 |
| 3 | B-24 | 唯一的功能性死局：撞上下文上限后无法继续；错误分类已经做对，缺的是恢复手段 |
| 4 | B-20 → B-21 → B-23 | 沙箱必须先有 seam，否则策略只能写死；审批依赖沙箱的三态决策 |
| 5 | B-22 / B-26 / B-36 | 输出治理与上下文注入，建立在 seam 与 compaction 之上 |
| 6 | B-33 / B-25 / B-37 / B-38 | 界面、生态与运维；不阻塞日常闭环 |
| 工程化 | B-41 / B-42 / B-44 | 穿插或阶段末集中 |

**为什么不把安全放第一**：沙箱影响的是"敢不敢跑不可信提示词"，而 compaction 影响的是"会话能不能继续"。后者是硬死局，前者是风险面；把死局先解掉，再回头补安全，收益更高。**但这不是不可推翻的**：如果用户更看重安全，`B-20 → B-21 → B-23` 可以整体提到最前面，与 1–6 没有依赖冲突。

**B-12 与 B-33 的先后**：Web 会话列表会扩大无鉴权暴露面，所以 B-33 开工前必须先拍 B-12（是否要 token、默认值、如何传给前端）。
